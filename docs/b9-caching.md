# B9. Кешування GET-запитів (Redis)

Списки, які фронтенд перечитує найчастіше, кешуються на сервері. Кеш прозорий для клієнта: відповідь та сама, лише додається заголовок `X-Cache`.

## Що кешується

| Ендпоінт                                      | Ключ (після `ws:<workspaceId>:`) | TTL  |
| --------------------------------------------- | -------------------------------- | ---- |
| `GET /api/workspaces/:ws/pages`               | `pages:<запит>`                  | 60 с |
| `GET /api/workspaces/:ws/tasks`               | `tasks:<запит>`                  | 60 с |
| `GET /api/workspaces/:ws/events`              | `events:<запит>`                 | 60 с |
| `GET /api/workspaces/:ws/overview` (зведення) | `overview:`                      | 15 с |

- `<запит>` нормалізований: параметри відсортовані, порожні відкинуті, дати в ISO, значення за замовчуванням (`skip=0`, `limit=20`) не відрізняються від відсутніх. `?q=a&priority=HIGH` і `?priority=HIGH&q=a` дають один запис.
- У кеші лежить лише `{ items, total }`. `nextLink` будується з кожного запиту окремо, інакше посилання з `Host` першого відвідувача потрапило б до інших.
- Зведення (`overview`) залежить від поточного часу («due soon», «running now»), тому має найкоротший TTL.

### Що НЕ кешується

- `GET /api/workspaces/:ws/calendar`: відповідь залежить від того, хто питає (Google-права конкретного користувача: `connected`, `editGranted`, `mine`, `editable`). Заголовка `X-Cache` у нього немає.
- Читання одного запису (`GET .../:id`), помилки та невалідні запити.
- Усе поза цими чотирма списками.

## Ізоляція тенантів

1. Кеш читається лише всередині обробника, тобто **після** `AuthGuard` і `WorkspaceGuard`. Не-учасник воркспейсу отримує `404` ще до кешу, навіть якщо запис «теплий».
2. `workspaceId` входить у кожен ключ, тож запити двох воркспейсів ніколи не збігаються.
3. Усі ключі воркспейсу мають спільний префікс `ws:<id>:`, тому одна операція `deleteByPrefix` очищає весь воркспейс.

Е2е-тести (`apps/api/test/cache.e2e-spec.ts`) перевіряють усе вище: чужий токен не бачить теплий кеш, запис в одному воркспейсі не скидає кеш іншого, календар не кешується і віддає різні права двом учасникам.

## Інвалідація

Після кожного запису, що може змінити списки, викликається `CacheService.invalidateWorkspace(workspaceId)`:

| Де                                                                                   | Чому                                                                                                        |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `TasksService` create / update / remove                                              | список задач, зведення                                                                                      |
| `EventsService` create / update / remove                                             | список подій, зведення                                                                                      |
| `PagesService` create / update / remove, імпорт Markdown, `NotesService`             | список сторінок, зведення                                                                                   |
| `BlocksService` create / update / remove                                             | у списку сторінок є `_count.blocks`                                                                         |
| `SyncService.apply` (редактор у реальному часі)                                      | змінює блоки і `updatedAt` сторінки                                                                         |
| `GoogleCalendarService`: синхронізація, зміна/створення/видалення події, відключення | імпортує або видаляє події й задачі (при відключенні очищаються всі воркспейси, куди імпортував користувач) |

Запис, який почався **до** інвалідації, але закінчив читання **після** неї, не кладеться в кеш (лічильник «епох» у `CacheService.remember`), тож застарілий список не «воскресає» після запису в тому ж процесі.

Що може лишитися застарілим, поки не мине TTL: імена виконавців у зведенні (зміна імені користувача не знає, у яких воркспейсах він згаданий) та запис в іншому екземплярі API, якщо Redis у цей момент був недоступний.

## Драйвери

`CacheService` (JSON, TTL, `deleteByPrefix`) працює поверх `CacheDriver`:

- **`RedisCache`** (`ioredis`): вмикається, коли задано `REDIS_URL`. Ключі мають префікс `nook:cache:`, видалення за префіксом робить `SCAN` + `UNLINK` (без `KEYS`). Без офлайн-черги і з короткими таймаутами: коли Redis лежить, команди падають одразу.
- **`MemoryCache`**: типовий (без `REDIS_URL`), його ж використовують тести. Обмежений 5000 записів, протухлі видаляються першими.

**Падіння Redis не ламає запити.** Будь-яка помилка драйвера (з'єднання, таймаут, зіпсоване значення) = «у кеші нічого немає»: запит читає БД і повертає `X-Cache: MISS`; у лог іде одне попередження на 30 с. Мовчазного переходу на пам'ять немає: з кількома екземплярами API локальні кеші розійшлися б з інвалідацією.

## Як побачити HIT / MISS

```bash
curl -si -H "Authorization: Bearer $TOKEN" "http://localhost:3000/api/workspaces/$WS/tasks?limit=50" | grep -i x-cache
# X-Cache: MISS   (перший запит)
# X-Cache: HIT    (повторний)
```

Створіть задачу (`POST .../tasks`) і повторіть запит: знову `MISS`. Для Redis: `docker compose -f infra/docker-compose.yml exec redis redis-cli --scan --pattern 'nook:cache:*'`.

## Запуск

```bash
docker compose -f infra/docker-compose.yml up -d redis   # порт 6380 на хості
echo 'REDIS_URL=redis://localhost:6380' >> apps/api/.env
```

У повному стеку (`docker-compose.yml`, `compose.prod.yml`) сервіс `redis` (`redis:7-alpine`, healthcheck `redis-cli ping`, `allkeys-lru`, 64 МБ, без збереження на диск) уже підключений, а `api` отримує `REDIS_URL=redis://redis:6379`.

## Вимір

Локально (5000 задач у воркспейсі, 200 запитів через supertest, «miss» включає інвалідацію перед кожним запитом):

| Запит             | Драйвер | без кешу (MISS) | з кешем (HIT) |
| ----------------- | ------- | --------------- | ------------- |
| `tasks?limit=100` | memory  | 5,1 мс          | 1,7 мс        |
| `overview`        | memory  | 5,1 мс          | 1,3 мс        |
| `tasks?limit=100` | Redis   | 8,3 мс          | 3,6 мс        |
| `overview`        | Redis   | 9,1 мс          | 4,3 мс        |

Різниця невелика, бо БД локальна і запити прості; вона росте з обсягом даних і відстанню до Postgres. HIT = розбір JSON + заголовки, без жодного SQL.

## Тести

- Юніт: `memory-cache.spec.ts` (TTL, префікс, ліміт), `redis-cache.spec.ts` (мок-клієнт: ключі, `EX`, SCAN/UNLINK, екранування glob), `cache.service.spec.ts` (нормалізація, гонки, відмова драйвера).
- E2E: `cache.e2e-spec.ts` (HIT/MISS, інвалідація кожним записом, Google-синхронізація, ізоляція тенантів і глядачів, відмова драйвера).
