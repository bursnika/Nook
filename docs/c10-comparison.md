# C10: WebSocket, Long Poll і Adaptive Polling

Один і той самий потік блок-операцій сторінки (`insert / update / move / delete`) Nook віддає клієнтам трьома способами. Усі три працюють поверх спільного журналу операцій і шини подій (`apps/api/src/realtime`), тому дані й порядок однакові, а різниця лише в транспорті.

| Транспорт        | Як працює                                                                                                 | Де в коді                         |
| ---------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------- |
| WebSocket        | Одне з'єднання на вкладку, сервер штовхає зміни одразу                                                    | `realtime.gateway.ts`, шлях `/ws` |
| Long Poll        | `GET …/sync/poll`: сервер тримає запит до 25 с і відповідає, щойно є зміни                                | `sync.controller.ts`              |
| Adaptive Polling | `GET …/sync/changes`: клієнт сам питає. Після активності кожні 400 мс, у тиші інтервал росте ×1,5 до 10 с | `sync.controller.ts` + клієнт     |

У застосунку транспорт перемикається в Settings (поле зберігається в `localStorage`), редактор переходить на новий без перезавантаження.

## Методика

Скрипт `apps/api/scripts/bench-sync.ts` (`pnpm --filter @nook/api bench:sync`):

1. Створює воркспейс і окрему сторінку для кожного транспорту.
2. Запускає `N` читачів (інші вкладки) з тим транспортом, який перевіряється.
3. Один письменник надсилає `W` операцій зі швидкістю `R` на секунду. У тексті кожної операції лежить час відправлення, тож затримка = момент отримання читачем мінус момент відправлення (годинник один, машина одна).
4. Після записів читачі `10 с` простоюють: тут видно ціну запитів, які нічого не приносять.
5. Сервер сам рахує запити, байти й CPU окремо по транспортах (`GET /api/sync-metrics`, лише для адміністратора платформи).

Середовище: один ноутбук (macOS), API зібраний `nest start`, Postgres у Docker, клієнти й сервер на одній машині, без мережевої затримки. Абсолютні числа залежать від машини, а співвідношення між транспортами стабільні.

## Висновки

- **Затримка.** WebSocket найшвидший: 12–19 мс p50. Long Poll додає один круг запит-відповідь (40–50 мс). У Adaptive Polling затримка визначається інтервалом: p50 ≈ 220 мс, p95 до 410 мс, тобто змінений блок з'являється з пів-секундним запізненням.
- **Навантаження.** WebSocket найдешевший по CPU (≈ 4–6 разів менше, ніж у HTTP-варіантів) і не створює запитів. Long Poll робить по одному запиту на кожну доставлену зміну на кожного читача (600 і 2000 запитів): кожна відповідь закриває запит, і читач одразу відкриває наступний. Тому він найдорожчий по CPU, хоч найточніший серед HTTP-способів.
- **Простій.** Long Poll і WebSocket у тиші майже нічого не коштують (запит висить, з'єднання відкрите). Adaptive Polling у тиші все одно ходить: 40 запитів за 10 с на 10 читачів і 198 на 50, але інтервал росте до 10 с, тож це значно менше за наївний polling раз на 400 мс.
- **Надійність.** HTTP-варіанти працюють за будь-яких проксі й корпоративних мереж, де WebSocket ріжуть. Усі три транспорти після обриву наздоганяють пропущене запитом `GET …/sync/changes?since=<seq>`, а повторна відправка операцій безпечна (вставка наявного id ігнорується), тож зміни не губляться.
- **Масштабування.** Шина подій живе в пам'яті процесу. Для кількох екземплярів API її заміняє Redis pub/sub (інтерфейс `RealtimeBus` не зміниться). Long Poll утримує відкритий запит на кожного читача, WebSocket утримує з'єднання, обидва тримають по одному сокету на вкладку.

## Що обрано за замовчуванням

WebSocket: найменша затримка й навантаження. Long Poll лишається як запасний варіант для мереж без WebSocket, Adaptive Polling для найобмеженіших середовищ (приспаний, поки вкладка прихована). Користувач може змінити вибір у Settings.

## Як повторити

```bash
# API зі збіркою (tsx не підходить, бо потрібні метадані декораторів) і адміном для метрик
ADMIN_EMAILS=bench@nook.local PORT=3200 pnpm --filter @nook/api exec nest start &
pnpm --filter @nook/api bench:sync -- --url http://localhost:3200 --listeners 10 --writes 60 --rate 4 --idle 10
```
